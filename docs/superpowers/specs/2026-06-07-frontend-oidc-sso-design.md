# 前端 OIDC SSO 统一改造设计

## 1. 背景

当前 `frontend/apps/platform-admin-web` 与 `frontend/apps/sso-test-app` 都已接入 IAM OIDC，但登录态模型并不统一：

- 两个应用都把本地持久化 token 作为主要登录依据
- `platform-admin-web` 主要依赖页面启动时的一次 `prompt=none` 检查
- `sso-test-app` 额外使用 iframe silent check 做状态补偿
- 两个应用的登录、登出、回调、失效处理策略不一致

直接结果是：

1. 一个应用登录后，访问另一个应用时不能稳定无感进入主页
2. 一个应用登出后，另一个应用不会及时收敛到登出状态

本次改造限定为：只改造现有前端应用，不新增 BFF；允许后端做必要增强；接受跨应用登出为最终一致，而非强实时一致。

## 2. 问题根因

### 2.1 跨应用免登录不稳定

根因不是 IAM 没有 SSO，会话能力已经存在于后端 `iam_sso_session` 中。真正的问题是前端没有统一围绕这个中心会话建模。

- `platform-admin-web` 登录按钮强制追加 `prompt=login`，会绕开已有 SSO 会话
- 两个应用都把“当前应用本地 token 是否存在”当作主要事实来源
- 访问另一个应用时，没有统一的“先向 OIDC 中心会话对齐，再决定是否展示登录页”的状态机

因此，应用 A 已登录后，应用 B 虽然理论上可借助 IAM 中心会话直接完成授权，但实际前端实现并不稳定。

### 2.2 跨应用登出不一致

根因是“本地 token 状态”和“中心 SSO 会话”混用，但缺少统一的失效收敛机制。

- 前端登出时会清本地状态
- 后端 `end_session` 会清 `iam_sso_session`
- 后端还会吊销 refresh token 和相关 SSO session
- 但另一个已经打开的应用可能仍然保留未过期 access token 和 UI 状态

结果是：中心会话已经退出，但另一个应用不会立刻知道，只有在重新发请求、切回页面或重新检查会话时才会收敛。

## 3. 目标与非目标

### 3.1 目标

本次改造目标如下：

1. 两个前端应用统一为标准 `OIDC Authorization Code + PKCE` SPA 模型
2. 一个应用登录后，访问另一个应用域名时可无感完成授权并进入主页
3. 一个应用登出后，另一个应用通过统一探测机制尽快收敛到登录页
4. 不新增 BFF，不引入应用侧服务端 session
5. 尽量复用现有 IAM OIDC 能力，只补必要后端增强

### 3.2 非目标

本次不追求以下能力：

1. 不追求纯前端条件下的跨应用强一致实时登出
2. 不引入每个应用独立的后端会话层
3. 不把所有业务 API 改造成通过网关或代理调用

## 4. 方案对比

### 4.1 方案 A：维持现状，局部修补

做法：继续保留两套现有逻辑，只分别修补个别登录和登出问题。

优点：改动最小。

缺点：

- 两个应用仍然维持不同认证状态机
- 后续继续出现边界不一致的概率很高
- 很难形成可验证、可维护的统一行为

结论：不采用。

### 4.2 方案 B：BFF + 服务端 session

做法：把两个应用改造成 BFF 模式，由服务端持有 token 和 session。

优点：

- 安全性和登出一致性最佳
- 更适合不同主域和 back-channel logout

缺点：

- 超出“只改造前端应用”的约束
- 需要新增服务端组件和新的部署形态

结论：本次不采用。

### 4.3 方案 C：统一纯前端 OIDC 状态机

做法：两个应用都统一到标准 SPA OIDC 模型，依赖 IAM 中心会话实现跨应用免登录，并通过统一的前端会话探测机制实现登出最终一致。

优点：

- 符合本次约束
- 能解决跨应用免登录问题
- 能把跨应用登出收敛到可接受的一致性水平

缺点：

- 仍然保留浏览器侧 token
- 登出只能做到最终一致

结论：采用此方案。

## 5. 总体设计

### 5.1 统一原则

两个前端应用统一遵循以下原则：

1. 都使用 `Authorization Code + PKCE`
2. 都依赖 IAM 的中心 SSO 会话完成跨应用免登录
3. 本地 token 只是当前应用的缓存，不再是唯一事实来源
4. 登录、回调、登出、失效处理、会话探测统一成一套状态机

### 5.2 登录态分层

在纯前端方案下，仍然需要明确两层状态：

1. IAM 中心 SSO 会话
   - 由 IAM 域名下的 `iam_sso_session` 表示
   - 决定用户访问另一个应用时是否可无感重新授权

2. 当前应用本地 token 状态
   - 由当前应用保存 access token、refresh token、id token 和用户上下文
   - 只表示“当前应用当前是否还能直接调用 IAM API”

设计要求是：前端不得再把第二层状态误当成第一层状态。

## 6. 前端状态机设计

### 6.1 统一状态

两个应用统一为以下认证状态：

- `checking`：正在判断是否可恢复或建立当前应用会话
- `authenticated`：当前应用已有可用 token，并完成必要的用户上下文加载
- `anonymous`：当前应用没有可用会话，需要展示登录入口

### 6.2 启动流程

应用冷启动时统一按以下顺序执行：

1. 读取本地 token 状态
2. 如果当前路由是 OIDC 回调，则优先处理回调
3. 如果本地 token 可用，则先进入 `authenticated`
4. 同时启动一次轻量会话对齐流程
5. 如果本地没有 token，则直接发起一次标准 OIDC 授权请求
6. IAM 若已有中心 SSO 会话，则无感回跳并建立当前应用 token
7. IAM 若无中心会话，则回到登录页

这里的关键变化是：访问应用时不再先把用户锁死在登录页，而是先尝试与 IAM 中心会话对齐。

### 6.3 登录流程

登录页点击“登录”时：

1. 生成 PKCE 参数
2. 跳转标准 `/authorize`
3. 不默认追加 `prompt=login`
4. 仅在用户明确执行“强制重新登录”操作时，才允许追加 `prompt=login`

这样可以最大化复用 IAM 已有中心会话，避免人为破坏单点登录体验。

### 6.4 回调流程

两个应用统一回调处理逻辑：

1. 校验 `code`、`state`
2. 校验并清理本地 PKCE 临时参数
3. 用 code 换 token
4. 写入统一的 auth store
5. 清理中间状态标记
6. 跳回首页

两个应用不再分别维护两套 silent callback 特例逻辑。

## 7. 跨应用免登录设计

### 7.1 标准链路

访问应用 B 时，如果应用 B 当前没有本地 token：

1. 应用 B 发起 OIDC `/authorize`
2. IAM 检查 `iam_sso_session`
3. 若中心会话有效，则直接完成授权并回调应用 B
4. 应用 B 建立自己的本地 token 状态并进入主页

因此，“A 已登录后访问 B 直接进入主页”依赖的是 IAM 中心会话，而不是 localStorage 共享，也不是 iframe 同步。

### 7.2 对现有实现的调整

需要移除或修改以下破坏 SSO 体验的行为：

1. `platform-admin-web` 登录按钮默认追加 `prompt=login`
2. `logged_out` 这类永久阻断再次会话探测的本地标记
3. 两个应用不一致的 silent check 入口和特殊分支

## 8. 跨应用登出设计

### 8.1 目标

纯前端方案下，登出目标定义为：

- 当前应用立即退出
- IAM 中心会话立即销毁
- 其他应用在下一次交互、恢复可见、请求失败或周期探测时收敛到退出状态

### 8.2 统一登出链路

点击退出时统一执行：

1. 尝试调用业务 logout 接口，吊销当前 refresh token
2. 清理当前应用本地 token 与用户上下文
3. 跳转 IAM `end_session`
4. IAM 清理 `iam_sso_session` 并吊销相关服务器端会话/refresh token
5. 跳回当前应用登录页

### 8.3 其他应用的收敛机制

另一个已经打开的应用通过以下机制收敛：

1. 冷启动检查
2. 页面从隐藏切回可见时检查
3. 接口返回 `401`、业务未认证码时立即清本地状态并回登录页
4. 可选低频周期检查

### 8.4 为什么不用前端广播作为主机制

`BroadcastChannel`、`localStorage storage event` 等机制只能覆盖同源场景，不适合不同主域。因此它们不能作为本次跨应用登出的一致性基础。若后续同源部署，可作为补充优化，但不写入主设计。

## 9. 会话探测设计

### 9.1 探测原则

会话探测的目标不是频繁刷新 token，而是确认“当前应用本地状态是否仍然和 IAM 中心会话一致”。

### 9.2 探测触发点

统一触发点如下：

1. 应用启动时
2. 页面恢复可见时
3. 关键认证接口失败时
4. 可选：每 60 秒到 5 分钟低频探测一次

### 9.3 探测行为

探测统一采用重新发起一次无感授权检查，而不是在两个应用里维持不同的 iframe 实现。

推荐行为：

1. 若当前已有本地 token，则先保持页面可用
2. 在后台发起一次轻量会话确认
3. 若确认中心会话仍有效，则保持当前状态或更新 token
4. 若确认中心会话已失效，则清空本地状态并跳登录页

这里允许实现上仍然使用静默回调页或隐藏 iframe，但要求两个应用共用同一套实现和状态机，不再各自演化。

## 10. 对现有代码的改造范围

### 10.1 保留

可保留的能力：

1. OIDC PKCE 基础工具函数
2. token exchange 与 refresh 基础逻辑
3. IAM 现有 OIDC Provider 与 `end_session`、`sso-login`、refresh token 吊销能力

### 10.2 重写或统一

需要统一或重写的模块：

1. `frontend/apps/platform-admin-web/src/utils/oidc.ts`
2. `frontend/apps/sso-test-app/src/utils/oidc.ts`
3. 两个应用的 `stores/authStore.ts`
4. 两个应用的 `pages/auth/Login.tsx`
5. 两个应用的 `pages/auth/AuthCallback.tsx`
6. 两个应用的 `utils/request.ts`
7. 两个应用的应用启动守卫逻辑与主路由逻辑

### 10.3 删除的行为

应删除以下行为：

1. 默认 `prompt=login`
2. 依赖 `logged_out` 之类本地永久阻断标记
3. 两套不一致的 silent check 状态标记命名和分支逻辑
4. 仅凭 persisted token 就长期认定“当前仍然已登录”的假设

## 11. 必要后端增强

虽然不新增 BFF，但后端仍需做必要增强，保证前端标准链路可用。

### 11.1 IAM OIDC 侧

需要确认或补齐：

1. `authorize`、`oauth/token`、`end_session` 对 SPA + PKCE 模式的稳定支持
2. `end_session` 后一定清理 `iam_sso_session`
3. `TerminateSession` 后应确保 refresh token 被统一吊销
4. 针对前端无感会话探测，提供稳定可依赖的返回行为

### 11.2 Client 配置侧

需要保证两个前端应用的 OAuth Client 配置明确且一致：

1. `redirect_uri`
2. `post_logout_redirect_uri`
3. `token_endpoint_auth_method`
4. PKCE 支持方式
5. 允许的 scope

## 12. 迁移策略

### 12.1 第一阶段：统一状态机

1. 先抽出两个应用共用的 OIDC 前端模型
2. 统一 auth store、回调、登录入口、登出入口
3. 移除 `prompt=login` 默认行为

验证：A 登录后访问 B，能稳定无感进入主页。

### 12.2 第二阶段：统一会话探测

1. 把两个应用不同的 silent check 统一为一套实现
2. 补齐冷启动、页面恢复、401 退登三类入口

验证：A 登出后，B 在下一次可见、请求或探测时能回登录页。

### 12.3 第三阶段：清理历史分支

1. 删除旧的本地标记与特判逻辑
2. 清理不再需要的状态字段和流程分叉
3. 补齐自动化测试

验证：两个应用认证行为完全一致，只保留业务 UI 差异。

## 13. 测试与验收

### 13.1 登录验收

1. 未登录访问任一应用，会自动走 OIDC 授权流程
2. A 登录后访问 B，可直接进入主页，无需再次输入密码
3. 刷新页面后仍能恢复当前应用状态

### 13.2 登出验收

1. 在 A 退出后，A 立即回登录页
2. 再访问 B 时直接到登录页
3. 若 B 已打开，则在下一次交互、探测或请求失败后退出

### 13.3 安全与行为验收

1. 不再默认强制 `prompt=login`
2. 不再使用永久阻断型本地标记破坏单点登录
3. refresh token 被正确吊销后，旧应用不能长期维持假登录状态

## 14. 风险与约束

1. 纯前端方案下，token 仍然存在浏览器侧，这是本方案接受的限制
2. 不同主域下不能依赖前端广播同步登出，这是浏览器模型限制
3. 登出为最终一致，不能对另一个已打开应用承诺瞬时同步 UI 退出
4. 若后续要求强一致跨应用登出，应重新评估 BFF 或 back-channel logout 方案

## 15. 最终结论

本次采用的设计为：

`纯前端 SPA + OIDC Authorization Code + PKCE + IAM 中心 SSO 会话 + 统一前端状态机 + 登出最终一致收敛`

该方案满足以下前提：

1. 只改造现有前端应用
2. 不新增 BFF
3. 接受登出最终一致
4. 使用现有 IAM OIDC 能力作为中心会话基础

在此基础上，`platform-admin-web` 和 `sso-test-app` 将从两套分叉的 OIDC 行为，收敛成一套可预测、可测试、可维护的统一前端 SSO 模型。
